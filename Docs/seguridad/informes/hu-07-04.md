## 3. Hallazgos

### M1. El reintento con otra clave técnica u otro `primerNumero` responde 200 «ya existía» (Media)

**Pasos**
```
POST /configuracion-dian/resoluciones  (dueño A, 2FA reciente)
{"id":"aaaaaaaa-0000-4000-8000-000000000001","clase":"factura","numero":"18760000001","prefijo":"SETP",
 "desde":990000000,"hasta":995000000,"vigenteDesde":"2019-01-19","vigenteHasta":"2030-01-19",
 "claveTecnica":"fc8eac42…"}                                  -> 201
mismo id y mismo cuerpo, "claveTecnica":"OTRACLAVE"           -> 200 {"id":"aaaaaaaa-…-000000000001"}
mismo id, sin claveTecnica                                    -> 200
mismo id, "primerNumero":994000000                            -> 200
mismo id, "hasta":995000001                                   -> 409 resolucion.id-en-uso   (este sí)
```
No sobrescribe: la fila conserva la clave original. Pero la app recibe un 200 de éxito. Un dueño que corrige una clave técnica mal copiada con el mismo id (la app lo reutiliza al reintentar) cree que quedó guardada. El CUFE de cada factura sale con la clave vieja y la DIAN rechaza todas las facturas del rango. Pasa lo mismo con `primerNumero`: el usuario cree que CONTA empieza en el número que escribió.

**Impacto**: una empresa (la del dueño). Integridad fiscal: facturas rechazadas sin aviso.

**Causa**: `api/src/modulos/facturacion/infraestructura/persistencia/configuracion/resoluciones-postgres.ts:63-74`. `mismaResolucion` compara número, prefijo, clase, rango y vigencia, pero ni la clave técnica ni el primer número.

**Corrección propuesta**: guardar una huella del pedido (SHA-256 del cuerpo normalizado, con la clave técnica incluida, como en `ventas.huella`) en una columna `huella`, y responder `resolucion.id-en-uso` cuando la huella no coincida. Otra opción: descifrar la clave guardada con su dato asociado y compararla en tiempo constante, y comparar `primerNumero` contra una columna `primer_numero` inmutable (no contra `siguiente`, que avanza con las ventas).

### M2. El NIT del facturador acepta 222222222222 (consumidor final) (Media)

**Pasos**
```
PUT /configuracion-dian/datos-fiscales  (dueño de D)
{"nit":"222222222222","razonSocial":"Ataque D S.A.S.","tipoDePersona":"juridica","responsabilidadesFiscales":["O-13"],
 "responsableDeIva":true,"direccion":{"codigoMunicipio":"11001",...},"correo":"a@b.co"}   -> 204
también "nit":"444444001" -> 204 y "nit":"100" -> 204
```
El NIT 222222222222 es el identificador genérico del consumidor final. Como NIT del emisor, cada venta a consumidor final queda con emisor igual a adquiriente, y la DIAN rechaza esas facturas (el NIT del emisor tiene que estar en el RUT y habilitado). Peor: con la primera venta el NIT queda fijo y solo soporte puede corregirlo.

**Impacto**: una empresa. Regla fiscal (consumidor final).

**Causa**: `api/src/modulos/facturacion/dominio/configuracion/datos-fiscales.ts:26`, que solo llama a `Nit.de` (`api/src/compartido/dominio/nit.ts:14-18`, que valida de 3 a 15 dígitos). No usa `consumidor-final.ts`.

**Corrección propuesta**: en `datosFiscalesDelFacturador`, rechazar con `configuracion.nit-generico` los identificadores genéricos de la DIAN (222222222222, y los 444444xxx de extranjeros si aplican) usando la constante de `catalogo/dominio/clientes/consumidor-final.ts`, llevada a `compartido/dominio`. Conviene además exigir el largo real de un NIT de persona jurídica (9 dígitos) cuando `tipoDePersona` es `juridica`.

### M3. Un PUT sin PIN revierte un PIN nuevo guardado al mismo tiempo (lost update) (Media)

**Pasos** (`a14-carrera-sw.mjs`, empresa D)
```
PUT /configuracion-dian/software/factura {"idSoftware":"…dd","testSetId":"…dd","pin":"VIEJO000"}  -> 204
en paralelo:
  PUT … {"idSoftware":"…dd","testSetId":"…ee"}            (sin pin: «conserva el guardado») -> 204
  PUT … {"idSoftware":"…dd","testSetId":"…dd","pin":"NUEVO7Z"}                           -> 204
resultado: pin_final = '0' (VIEJO000) en 5 de 20 rondas
```
Los dos responden 204, pero queda el PIN viejo. Pasa con dos codueños que guardan a la vez, o con la app que manda el formulario dos veces (doble toque o reintento) mientras otra pantalla cambia el PIN. El dueño cree que tiene el PIN nuevo. La firma usa el viejo y la DIAN rechaza los envíos.

**Impacto**: una empresa. Integridad del secreto.

**Causa**: `api/src/modulos/facturacion/aplicacion/configuracion/guardar-software.ts:21-29`. Lee el guardado sin bloqueo (`softwares-postgres.ts:13-14`, `select … limit 1` sin `FOR UPDATE`) y después el upsert (`softwares-postgres.ts:41-44`) escribe `pin_cifrado` con el valor leído antes.

**Corrección propuesta**: cuando `pin` es null, no incluir `pin_cifrado` ni `pin_final` en el `SET` del `ON CONFLICT DO UPDATE` (y fallar si no hay fila previa). O leer con `SELECT … FOR UPDATE` dentro de la misma transacción.

### B1. El año `0000` en la vigencia produce 500 (Baja)

```
POST /configuracion-dian/resoluciones {"id":"aaaaaaaa-0000-4000-8000-000000000100",...,"vigenteDesde":"0000-01-01","vigenteHasta":"2030-01-01"}
-> 500 {"codigo":"servidor.falla","mensaje":"Algo salió mal. Intenta de nuevo.","referencia":"b2f88aee-…"}
api.log: falla b2f88aee-…: Error · SQLSTATE 22008
```
El registro no filtra valores. Es una falla no controlada que sirve para hacer ruido en las alertas.
**Causa**: `api/src/modulos/facturacion/dominio/entidades/resolucion-de-numeracion.ts:60-62`. `esFecha` acepta el año 0000 porque `Date` de JS sí lo tiene y PostgreSQL no.
**Corrección**: exigir un año dentro de un rango razonable (por ejemplo, de 2000 a 2100) en `esFecha` o en `resolucionNueva`. Eso tapa también parte de B4.

### B2. El parser de JSON devuelve el PIN en el mensaje de error (Baja)

```
curl -X PUT localhost:3999/configuracion-dian/software/factura -H 'content-type: application/json' -d '{"pin":FUGAPIN2468}'
-> 400 {"message":"Unexpected token 'F', \"{\"pin\":FUGAPIN2468}\" is not valid JSON","error":"Bad Request","statusCode":400}
   sin Cache-Control: no-store
```
Pasa sin sesión (el cuerpo se lee antes de la guarda). La respuesta vuelve a quien envió el cuerpo, así que no es una fuga a terceros. Pero rompe la regla «ningún mensaje repite lo recibido» y deja el PIN en cualquier registro de errores del cliente o de un proxy. No llegó a `api.log` (se buscó `FUGA`: 0 coincidencias). El formato tampoco es el contrato `{codigo, mensaje}`.
**Causa**: `api/src/compartido/presentacion/fallas/filtro-de-fallas.ts:21-24` devuelve tal cual el `BadRequestException` que arma Nest con el `SyntaxError` del body-parser.
**Corrección**: en `FiltroDeFallas`, cuando la excepción viene de un `SyntaxError` del parser, responder `{"codigo":"peticion.json-invalido","mensaje":"El cuerpo no es JSON válido"}` con `Cache-Control: no-store`. Es transversal: aplica a toda la API, no solo a esta historia.

### B3. El NIT cambia si hay una venta en curso sin confirmar (Baja)

**Pasos** (`a8-nit.mjs`)
```
conn conta_app: BEGIN; UPDATE resoluciones … siguiente+1; INSERT venta y línea en A;   (sin COMMIT)
PUT /configuracion-dian/datos-fiscales {"nit":"800197268",...}  (dueño A)   -> 204
COMMIT de la venta
SELECT: nit = 800197268, ventas = 1
PUT … {"nit":"900373076"}  -> 409 configuracion.nit-con-ventas   (ya no se puede volver)
```
La venta real lee el emisor (`numeracion-postgres.ts:17`) sin bloqueo y arma el documento con el NIT viejo, mientras el cambio de NIT se confirma. El resultado es una venta firmada con un NIT que ya no es el de la empresa, y el NIT queda congelado en el nuevo. La ventana dura milisegundos y solo existe en la primera venta, de ahí la severidad baja.
**Causa**: `api/migraciones/0012_configuracion_dian.sql:22` (el `EXISTS` no ve ventas sin confirmar) y `api/src/modulos/facturacion/infraestructura/persistencia/ventas/numeracion-postgres.ts:16-19` (el emisor se lee sin `FOR SHARE`). En la API, `guardar-datos-fiscales.ts:18-20` tiene la misma lectura previa sin bloqueo.
**Corrección**: leer el emisor con `SELECT … FOR SHARE` dentro de la transacción de la venta. El `UPDATE` del NIT espera a que la venta confirme, y entonces el trigger (consulta nueva en READ COMMITTED) ya la ve y rechaza el cambio.

### B4. Validación fiscal floja en datos fiscales y resoluciones (Baja)

Aceptados con 204 o 201:
- `codigoMunicipio` `99999` y `00001` (no existen en el DANE); `05001` (Medellín) con `departamento: "Bogotá"`.
- `responsabilidadesFiscales: ["R-99-PN","O-13"]` (R-99-PN es «no aplica», y aquí va junto a gran contribuyente).
- Resolución con `vigenteDesde: "0001-01-01"` y otra con `vigenteHasta: "9999-12-31"`. Como `resolucionVigente` prefiere la de `vigenteDesde` más reciente (`numeracion-postgres.ts:43`), un error de tipeo con vigencia hasta 9999 queda como la resolución activa y no se puede retirar (solo taparla con otra).

**Causa**: `datos-fiscales.ts:37-39` (solo revisa que el código no termine en 000), `datos-fiscales.ts:30-36` y `resolucion-de-numeracion.ts:40-42`.
**Corrección**: validar el código DANE contra la tabla de municipios y derivar de ella el departamento. Rechazar R-99-PN combinada con otras responsabilidades. Limitar la vigencia a un rango plausible (la DIAN autoriza por un plazo de meses a pocos años).

### B5. Sin tope de escrituras ni de resoluciones (Baja)

40 `PUT /preferencias` seguidos dieron 40 respuestas 204 y 40 filas en la bitácora. 30 `POST /resoluciones` seguidos dieron 30 respuestas 201. El GET devuelve las 45 resoluciones de A sin paginar (12 KB). Con una sesión robada dentro de los 10 minutos de 2FA reciente se pueden insertar miles de resoluciones que nunca se borran y llenar la bitácora, de modo que los 10 cambios visibles tapen el cambio real (repudio práctico).
**Causa**: no hay limitador en `configuracion-dian.controller.ts` (comparar con los topes diarios de `ventas` y `miembros`), y `resoluciones-postgres.ts:22-24` no pone límite.
**Corrección**: un tope por empresa y por día (por ejemplo, 20 resoluciones y 200 escrituras), un tope total de resoluciones vigentes, y en la bitácora agrupar o mostrar las de seguridad (PIN, resolución) aparte de las preferencias.

Otras de la cola que se probaron:
- `verificada_en` en el futuro (solo por base o por un reloj desfasado): la sesión queda «reciente» hasta 10 min después de esa hora futura (se escribió con `verificada_en = now()+50 min`). ## 6. Notas y límites

- La emisión completa (abrir el PIN guardado en `ConfiguracionDianGuardada` para firmar) no se pudo ejecutar de punta a punta: la venta de B quedó en cola con `AccesoDianNoConfigurado` porque el entorno local no tiene certificado (llega con HU-07.02). El dato asociado se comprobó aparte, descifrando las filas guardadas con `CustodiaAesGcm` compilada y la clave desechable del entorno local.
- El límite de acceso por IP (20 cada 10 min) se agotó en la preparación. Con `trust proxy 1`, en local la API acepta un `X-Forwarded-For` escrito por el cliente, y así se siguió probando el 2FA. En Render el proxy agrega la IP real y cuenta esa. Pero si hay otro salto delante (Cloudflare), un solo salto de confianza contaría la IP del proxy intermedio. Conviene revisarlo, aunque queda fuera del alcance de esta historia.
- Datos de prueba que quedan en la base local: empresas A, B, C y D, 45 resoluciones en A, una venta sembrada en A y en B, y una venta por API en B.

## 7. Reverificación (2026-11-28, base recreada y API reconstruida)

## 8. Cierre después de la reverificación

- **B3:** el 500 quedó corregido. El trigger `nit_fijo_con_ventas` ahora nombra su restricción, y `DatosFiscalesPostgres.guardar` la traduce a `409 configuracion.nit-con-ventas` dentro de un punto de guardado. Lo cubre la prueba de integración «si la venta en curso se confirmó primero…».
- **B4 (lo que sigue abierto):** que el municipio exista y que su nombre coincida con el departamento necesita el catálogo DANE completo (unos 1.100 municipios). Queda para HU-07.01, donde la lista de pasos revisa los datos contra la DIAN. Hoy se exige que el código empiece con un departamento real y que no termine en 000.
- **El cupo de B5 cuenta los intentos inválidos y vive en la memoria de cada instancia.** Se acepta así: Render gratis corre una sola instancia. Pasará a la base cuando haya más de una (HU-06.04, adaptador durable).
- **Pendientes que no son de esta historia:**
  - el `X-Forwarded-For` que la API acepta con `trust proxy 1`;
  - un CHECK `verificada_en <= now()`;
  - `Cache-Control: no-store` en el 400 de JSON mal formado.
